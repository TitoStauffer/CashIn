# Hosted PR quality orchestration

## Current state

`tools/github-reviewer/src/agent-orchestrator.ts` implements the provider-neutral orchestration policy. It requires current-head CI and Sonar evidence, runs Code Review before QA, requires a formal GitHub Code Review decision before QA, and runs a deterministic Quality Gate Coordinator only after QA approves. That module describes the `full` track only: the track is decided by the production stage CLI, as **Review tracks** below sets out, and on the `light` track the Coordinator runs without QA. The production stage CLI consolidates current authenticated evidence without a model call; Code Review and QA run on the selected model runtime (Claude Code by default, Codex as fallback). Each agent result must identify the same full commit SHA and include a report. Code Review also proves coverage of every changed file and risk area; QA records a result and evidence for every acceptance criterion. The current HEAD is re-read before and after agent execution, stale or incomplete evidence is rejected, and failures return `INCONCLUSIVE` without proceeding to dependent stages.

The orchestrator receives infrastructure adapters for GitHub, execution locking, agent execution, and report publication. It does not load a model SDK, contact an AI service, create a GitHub review on its own, or merge a pull request. Tests use adapter fakes and do not represent hosted validation.

**Selected runtime: Claude Code CLI (default) with the maintainer's Claude subscription; Codex CLI with ChatGPT Plus authentication remains available with `AGENT_RUNTIME=codex`.** Claude Code runs with `-p --output-format stream-json --verbose --json-schema`, no tools (`--tools ""`), no MCP servers (`--strict-mcp-config`), no persisted session, only the empty project setting scope (`--setting-sources project`), isolation settings that disable all hooks and auto-memory and exclude every `CLAUDE.md`/rules file, its own `--system-prompt` replacing the default Claude Code prompt, and an empty temporary working directory. The adapter does not rely on these flags alone: it reads the session `init` event and rejects the result when the session reports any tool other than the CLI-internal `StructuredOutput` mechanism used by `--json-schema`, any MCP server, or any executed hook. Its prompt budget is 2,000,000 bytes because the models expose a 1M-token window. The Codex description below applies when that fallback is selected. The private repository uses a persistent Windows self-hosted runner under the signed-in Windows account. The Codex CLI reuses the ChatGPT-managed authentication already stored on that machine; it does not use an OpenAI API key. Model requests consume the account's Plus/Codex usage limits and are not unlimited. The runner is registered to this repository, starts at Windows logon, and is kept online while the machine is running.

The hosted agent integration has been validated end to end on the configured self-hosted runner. The workflow runs only after the complete `CI` workflow succeeds for an internal pull request; CI already sequences PR metadata validation, API/Web/automation tools (the `GitHub Reviewer` check) and SonarQube. Before any Agent call, the stage compares the base SHA with the HEAD and fails closed unless the branch contains the current `master`. Metadata edits run the separate trusted `PR title` workflow without checking out PR code. A substantive human edit reruns the CI associated with the same HEAD after validation; checkbox-only and App-authored checklist edits skip recovery and never trigger or cancel agent orchestration. The CI title job reads the current PR metadata, so rerunning an initially blocked CI recovers a corrected title. The workflow can also be dispatched manually from `master`. All six reader/publisher checkouts leave `ref` unset so `actions/checkout` preserves the trusted event ref and its immutable SHA. Passing a raw SHA explicitly is avoided because it discards the named ref during validation on the Windows runner; manual dispatch remains guarded to `refs/heads/master`. The workflow fetches PR metadata and review inputs through a read-only Actions token, and never checks out or runs PR code. The model process (Claude Code by default, with the isolation above; Codex with `--sandbox read-only --ignore-user-config --ephemeral --disable shell_tool` when selected) receives the supplied review evidence but cannot read runner files, execute commands or load local configuration. The self-hosted agent jobs receive only a read-only Actions token; the model process receives neither the Actions token nor GitHub App credentials. Separate GitHub-hosted publisher jobs receive App credentials only after validating the structured result, the current PR SHA, and a fingerprint recalculated with the read-only Actions token. Before editing a responsible checkbox, the publisher reloads the PR and evidence and revalidates the HEAD and fingerprint. Fork PRs are ineligible for this self-hosted runtime.

The runner itself is trusted private infrastructure and must remain restricted to this repository and the `codex-plus` workflow label. The Claude Code and Codex authentication files on the runner are sensitive: it is not copied to GitHub Secrets, repository files, or artifacts. A shortcut in the signed-in user's Windows Startup folder starts the runner after sign-in; shutdown or sign-out makes it unavailable until the next login. Installation, startup and repair are versioned in [`tools/github-runner`](../tools/github-runner/README.md); a Claude Code `SessionStart` hook in `.claude/settings.json` starts the runner when it is installed but stopped. The hook executes only the copy of `ensure-runner.ps1` installed under `%LOCALAPPDATA%\CashInGithubRunner\scripts`, which only the installer writes. Opening a session on an untrusted branch therefore never runs that branch's runner scripts on the machine that holds the agents' credentials. The workflow serializes work by PR (falling back to the workflow-run branch when GitHub omits the PR number) and each agent stage is a separate job.

Completed evidence is durable in App-authored GitHub reviews and PR comments. Reports carry a stable marker for stage, full HEAD SHA, and a SHA-256 fingerprint of the review inputs: the base commit, PR title/body, exact diff, summarized CI/Sonar states, and `AGENTS.md` read from that base commit. The publisher and Merge Readiness independently reload and fingerprint those inputs before accepting or writing evidence. A retry reuses a valid current result, updates an existing report comment instead of posting a duplicate, and reuses `INCONCLUSIVE` outcomes unless manual dispatch explicitly enables `retry_inconclusive` after the blocker is resolved. Formal Code Review is reused only when the latest App review is on the same SHA and has the same decision and body. Artifacts only transfer a result between jobs in one run; they are not the persistent ledger. If a SHA or input fingerprint differs, the old result is not reused. Transient GitHub API failures stop the affected stage and the next run reconciles from the durable review/comment state.

PR title, description, and diff are treated as untrusted. A deterministic guard blocks several direct instruction-override patterns as `INCONCLUSIVE`, and tests verify those cases; this is a heuristic, not proof of model immunity. The model can still misjudge code without an obvious injection string. The orchestration never merges, and PM must perform the separate final Merge Readiness and human workflow checks. If a future policy requires zero model-based approval risk, replace automatic model approvals with an independent human approval gate.

DEV-44 remains open until the workflow is merged, runner labels and secrets are verified remotely, a real low-risk run completes, and the reports and formal review are confirmed by Merge Readiness. No merge should be performed solely to validate this workflow.

## Review tracks

Each round is classified as **full** or **light** by `tools/github-reviewer/src/review-track.ts`, from the changed-file list the privileged job reads from `/pulls/{n}/files`. The Pull Request body never participates.

The rule allowlists what is inert instead of listing what is sensitive. A change is light-track only when **every** changed file is `*.md`, `*.test.*` or `docs/knowledge/context-map.json`. Everything else is full-track: migrations, manifests, lockfiles, build configuration, Dockerfiles, `compose.yaml`, fixtures, shared test helpers, the Vitest setup, the Jira dispatcher, the workflows and the readiness evaluator itself — and a directory that does not exist yet.

The first implementation had the opposite shape, listing the sensitive prefixes, and the Code Review of PR #91 proved it unsafe: `apps/api/migrations/**`, the application manifests and `compose.yaml` all change runtime and all sat outside the list, so a migration or a production dependency bump would have reached merge without QA. With an allowlist, a path nobody classified demands the full track by omission instead of escaping QA by omission.

The light track skips **QA only**, which is the single model stage on the serialized self-hosted runner. Code Review always runs, CI always runs in full, and the deterministic Quality Gate Coordinator runs on both tracks: it makes no model call, and its published report is the App-signed record that states the track and the files that determined it.

Failure modes are closed by construction. An empty or unusable changed-file list classifies as full. The Coordinator throws rather than deciding when the list is absent. In the workflow, QA is skipped only when the track is a confirmed `light`, the Coordinator demands that QA was genuinely skipped rather than failed, and the final confirmation refuses an absent or unknown track instead of reading it as "not full". `Merge Readiness` recomputes the classification itself, at the start and at the end of the evaluation, and blocks when the two disagree; it never takes an agent's word for the track. On the light track a QA report that belongs to the current SHA and context and is not approved still blocks. A report that is missing, stale or unstructured is treated as absent, because it is not evidence about this revision: blocking it stranded a Pull Request that touched runtime, published QA and then reverted the runtime part, since nothing republishes that report once QA no longer runs — and the Coordinator already ignored it, so the two evaluators disagreed.

Because the classification is a pure function of the changed-file list, and that list already feeds the context fingerprint, a Pull Request that receives a runtime commit moves the fingerprint, invalidates prior evidence and demands the full track at the new HEAD. There is no stored verdict that could keep the cheaper track alive.

## Required adapter contracts

API/Web/automation-tools review inputs also include verified Actions run/job steps bound to the same repository, PR, CI workflow and exact HEAD SHA. The workflow token has `actions: read` for all six agent reader/publisher jobs and Merge Readiness. The context supports three CI jobs and four snapshots: the CI workflow plus scripts from the API, Web and automation-tools package manifests. Snapshots preserve the original hashes and the test/no-skip scripts while omitting environment values; package snapshots expose scripts only. The `GitHub Reviewer` check is configured for all current PRs and must pass on the current SHA under Actions App `15368` before the agents start or Merge Readiness can approve. Readers accept `Automation Tools` as a rollout-compatible alias. These additions are untrusted source context, never executed, and participate in the durable fingerprint. The injection heuristic is intentionally restricted to the PR title, description and newly added diff lines; it does not scan complete source, vault or CI snapshots. Step/configuration changes invalidate prior evidence; timestamps, links and equivalent rerun IDs do not. The loader does not fetch raw logs or infer assertion counts. A successful test/no-skip step must be assessed against its configuration, and QA may remain `INCONCLUSIVE` when acceptance evidence is insufficient. Unsupported sources, mismatched SHA/identity and API failures fail closed. A job whose step list arrives empty is re-read a bounded number of times before the loader decides, because the step list can lag the job's published conclusion; exhausting those attempts still fails closed, so a delay never becomes an approval. See the [reviewer README](../tools/github-reviewer/README.md#verified-ci-execution-context) for limits and supported configuration formats.

Workflow projection accepts the repository's block-style YAML subset: simple keys, scalar lists and indented literal/folded scalar blocks. Flow mappings at any depth (including JSON), quoted/complex keys and multiline quoted values fail closed before projection. Supported single-line GitHub expressions and scalar script blocks remain intact; other valid YAML formats may be rejected deliberately.

A hosted runtime must implement the `AgentOrchestratorDependencies` interface and provide:

- `readHeadSha` and `readPrerequisites` using GitHub evidence for the target PR.
- Per-repository/PR/SHA/agent idempotency backed by App-authored formal reviews and marked PR comments, with GitHub Actions concurrency and retry recovery after a runner is interrupted.
- `executeAgent` for the independently authorized Code Review, QA, and Quality Gate Coordinator roles. It must return a structured decision, exact SHA, and Markdown evidence.
- `submitFormalCodeReview` using a GitHub identity authorized to review and distinct from the PR author. The review body carries the Code Review findings; report comments alone are not formal reviews.
- `publishReport` by reusing the DEV-40 publisher for Code Review inconclusive reports, QA, and Quality Gate Coordinator reports; it must re-check the PR head before publishing and update a matching marked comment.

No adapter may receive a credential that is unnecessary for its role. Untrusted PR code must never run in a privileged job. A model/agent adapter should receive only the diff and the read-only context needed for analysis, not execute PR scripts. GitHub App credentials must be isolated to the narrowly scoped action that submits a review or publishes a report.

## Activation checklist

1. Merge the DEV-44 workflow and runtime implementation to `master`.
2. Confirm the repository secrets `CASHIN_APP_ID`, `CASHIN_APP_INSTALLATION_ID`, and `CASHIN_APP_PRIVATE_KEY`, plus the `CASHIN_APP_BOT_LOGIN` repository variable, are available to the workflow.
3. Validate a low-risk internal test PR after successful CI, confirming the real model CLI ran isolated (Claude Code: session reported no tools beyond `StructuredOutput`, no MCP servers and no hooks; Codex: shell tool disabled) on the current SHA and the Code Review formal review, QA report, and Coordinator report were published.
4. Confirm Merge Readiness re-evaluates after the reports and accepts only evidence for the same current SHA. Test a new commit and ensure old evidence no longer satisfies the gate.
5. Confirm timeout, duplicate event, and runner-unavailable outcomes fail closed. Do not enable merge automation as part of this work.
6. Only after these checks, document the workflow as active and close DEV-44. The workflow never performs merge or Jira transitions.

## Local tests

From `tools/github-reviewer`:

```powershell
npm ci
npm test
```

The unit tests validate sequencing, durable marker parsing, stale SHA/context rejection, duplicate comment updates, API failure handling, prompt-injection heuristics, Codex shell-tool disablement and the Claude Code isolation contract (arguments plus the runtime session check) using fakes. They do not make network requests, publish GitHub reviews/comments, invoke a model CLI, or prove that the self-hosted runner works. End-to-end runs consume the Claude subscription (default) or the ChatGPT Plus/Codex allowance (fallback). `actionlint` and `zizmor` validate workflow syntax and security patterns but do not verify remote runner state, GitHub App secrets, or model behavior.
